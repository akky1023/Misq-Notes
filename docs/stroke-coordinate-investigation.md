# ストロークの線端が位置によって角張る問題（2026-11-02）

## 結論

対象端末で、Ink 1.0.0のGPUメッシュ描画が丸い線端を欠落させる現象を再現した。同じ入力のストロークでも、移動先によって線端が丸くなったり斜めに切れたりする。保存された輪郭には丸い線端が残っており、輪郭をパスとして描画すると欠落しない。

メッシュの数値処理とGPUドライバーのどこで欠落するかという内部原因までは確定していない。確認できた不具合の経路を回避するため、アプリの描画方式をInkのパス描画へ統一した。

## 実データでの確認

- ユーザーが示した黄色い矢印は5か所あり、その周辺の9ストロークを調査した。
- 対象ノート1冊だけを読取り専用の調査ツールでストリームコピーし、コピー中の元データと取得後のコピーのSHA-256一致を確認した。
- 調査終了後も本番ノートを再取得し、調査前とファイル全体のSHA-256が一致することを確認した。
- 本番APKは更新せず、独立した検証アプリの画面で各ストロークを8位置に移動して描画した。
- 実機のPixelCopyでGPUの表示結果を取得し、メッシュ描画とパス描画を比較した。
- メッシュ描画では線端の欠落と位置依存を確認し、パス描画では丸い線端が描画されることを確認した。
- 始点付近で輪郭を生成し直すだけではメッシュ描画による欠落は回避できなかった。後の小さな切れ込みの再現検証により、現在はパス描画と局所座標での輪郭生成を併用している。詳細は [小さな欠けの原因と対策](stroke-small-notch-investigation.md) を参照。

取得したノート、入力データ、比較画像はGit管理対象外の `captures/stroke-position-20261102/` に保存している。外部サービスへの送信は行っていない。

## 修正内容

- `InkStrokeRenderer` に描画器の生成を集約し、Ink 1.0.0の `forcePathRendering` を使用する。
- 書きかけの線、完成した線、星の点滅、プレビュー、書き出し、サムネイル、マージ画面に同じ描画方式を使う。
- 保存データ、ブラシ設定、入力点、筆圧、ファイル形式は変更しない。
- 既存のRenderNodeキャッシュは引き続き使用する。

## 回帰確認

`CopiedStrokePositionTest` は保存ノートを開かず、合成ストロークまたは明示指定したストロークのコピーだけを扱う。GPUの表示結果をソフトウェア描画の輪郭と比較し、輪郭内部の欠落を検出する。実データを指定しない通常実行では、コピーを使用する検査だけをスキップする。

`strokePositionUseMesh=true` を指定すると旧方式で同じ検査を実行できる。実データの入力ファイルはテストソースに含めない。

- 単体テスト268件は失敗0・エラー0・スキップ1。
- 実機テスト14件はすべて成功。実データ9本×8位置の72条件で、参照輪郭の内部画素の欠落は0だった。
- 同じ実データ検査を旧メッシュ方式で実行すると、最初のストロークで内部画素7,288個の欠落を検出して失敗した。
- 合成ストロークの検査も成功。こちらは旧方式でも成功する通常入力の互換確認であり、不具合を検出する回帰確認には実データのコピーを使用した。
- lintはエラー0・警告12件。検証APKのビルド・applicationId・日本語／英語名・署名を確認した。

結果は `.tools/stroke-position/renderer-final-build.log`、`.tools/stroke-position/renderer-final-device.log`、`.tools/stroke-position/renderer-mesh-copied-regression.log` に記録している。

## 検証の限界

今回の端末でのコピーを使った再現・描画確認であり、本番APKの更新はしていない。実際のペンでの新規入力や長時間の講義中の動作、他機種での描画性能は別途確認が必要。保存ファイルを外部へ移す際のクラッシュは今回の修正対象に含めていない。
