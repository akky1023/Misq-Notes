# ノートの低速化と遅延終了の調査（2026-11-16）

外部同期の一覧取得で起きるJava OOMを再現し、修正後の30分試験と保存データの再読込を確認した。一方、高密度ストロークの再表示で数秒の描画待ちが残るため、依頼全体を修正完了とはしていない。

## 終了記録で確認したこと

Xiaomi Pad 7（7b42a7e6、Android 16）の本番 `net.neomenia.misqnotes` 0.7.0から、既存の終了履歴とcrashバッファを読み取った。過去の発熱調査の結果は、今回の終了原因の証拠には使っていない。

| 日時（端末の日本時間） | プロセス | 記録 |
| --- | --- | --- |
| 11/13 21:35:21 | Misq notes | Java OOM。外部同期の `ImmutableNoteTransport.rememberObject` で集合へ追加中 |
| 11/16 16:04:05 | Misq notes | Java OOM。外部同期の `PackedDocumentFiles.children` でUri生成中 |
| 11/16 17:24:30 | Misq notes | Java OOM。同じ外部同期の一覧取得経路 |
| 11/16 17:29:36 | ExternalStorageProvider | Java OOM。子ドキュメントの列挙中。アプリとは別プロセス |

本番アプリの上記3件は終了履歴の `APP CRASH(EXCEPTION)` と例外ログが一致し、Javaヒープ上限はいずれも256 MiBだった。ANR・native crash・OSのメモリ不足による強制終了とは区別できる。別の日時にはユーザー操作による終了やパッケージ更新もあるため、全終了をOOMとは数えない。

割り当てに失敗したスタックだけでは、保持元を特定できない。以下の検証版での比較を合わせて、外部同期一覧の保持・生成量を修正対象とした。発熱による速度低下の併発や、すべての低速化が同じ原因であることは確定していない。

## 再現と修正

`ExternalSyncBenchmarkTest.repeatedLargeInventoryWithSmallNote` は、筆跡ゼロのノートと、多数の無関係な外部オブジェクト名を使う。専用DocumentsProviderが名前を遅延生成するため、25万ファイルを実際に作ったり、本番保存先に書いたりする必要はない。各反復でサムネイルとコミットを公開し、最後に別のストアへ受信・再オープンして整合性を確認する。

修正前後の短い比較は、同じ端末・同じテストAPK・同じ仮想ファイル名・256 MiBのJavaヒープ上限で実施した。

| 条件 | 修正前 | 修正後 |
| --- | --- | --- |
| 15万背景ファイル・6反復 | 成功。ただし反復後のJava使用量は約141〜183 MB | 未比較 |
| 25万背景ファイル・6反復 | 初回約210 MB、2回目の一覧取得中にOOM、28.6秒でテスト失敗 | 6反復とコールド受信・整合性検証に成功、48.6秒 |
| 25万背景ファイル・30分指定・反復間15秒放置 | 2回目の一覧取得中にOOM、45.5秒でテスト失敗 | 91反復とコールド受信・整合性検証に成功、準備・最終検証込み1818.9秒 |

上表のMBはログのbytesを10進換算した値で、GC直後の生存量やピーク値ではない。OOMはJUnitが捕捉したため、テスト失敗とプロセスの異常終了を同一視しない。本番では同じ一覧取得経路の未捕捉OOMが終了記録に残っている。

一覧の保持方法と集合の更新方法を同時に変更した比較であり、それぞれ単独の改善率は測っていない。

30分比較の開始時のバッテリー温度は両版とも35℃。修正後の採取中も35℃、thermal statusは0だった。反復直前のJava使用量は2回目の130.8 MB、3回目の126.9 MBから、最終回127.2 MB。反復直後の記録値は136.9〜170.2 MBで、最終回152.3 MBだった。公開履歴と小さなサムネイルは反復ごとに増える条件であり、厳密に同一の生存オブジェクト集合ではない。

30分区間の後、本番保存先は変更せず名前の件数だけを確認し、約20.8万項目だった。採取した終了記録と、大量の無関係なファイル名を使う再現条件に整合する。個別statを伴う`find`は長引いたため自分の集計プロセスだけを停止し、その途中件数は採用していない。`ls -1f`の行数を参考値として保存した。件数採取と重なった過去の区間でMediaProvider 189%（1コア=100%）のCPU記録があったが、これをMisq notesのCPU時間には加算していない。

修正内容は次のとおり。

- `PackedDocumentFiles` は各ファイルのUriを保持する代わりに名前とdocument IDを保持し、読み書きするファイルのUriだけを生成する。
- 一覧取得中の中間Mapの複製を取り除き、名前とIDが変わらない項目は前回のレコードを再利用する。
- `ImmutableNoteTransport` は公開済みの名前を並行アクセス可能な集合へ追加し、オブジェクトと検証ファイルの追加ごとに外部一覧全体を複製する処理を取り除く。
- 一覧変更の判定は直前の一覧と比較し、判定専用に旧世代の一覧を保持しない。

ファイル名の全件確認、検証ファイルの確認、オブジェクトのハッシュ照合、破損・欠落時の拒否は引き続き行う。本体保存の500msウィンドウ、進行中の書き込み、Format 3の永続化順序には変更を加えていない。

## 長時間計測

検証用packageは `net.neomenia.misqnotes.probe`。インストール済み検証版と同じdebug署名でAPKを署名し、データを残したまま更新した。本番アプリの更新は行っていない。

次のコマンドで、反復上限または時間上限まで実行する。時間は試験区間の目標であり、準備・最後の受信検証は別にかかる。

```powershell
adb shell am instrument -w -r `
  -e class jp.handwriting.note.storage.ExternalSyncBenchmarkTest#repeatedLargeInventoryWithSmallNote `
  -e measureLargeInventory true -e backgroundObjects 125000 `
  -e durationSeconds 1800 -e idleSeconds 15 `
  net.neomenia.misqnotes.probe.tests/androidx.test.runner.AndroidJUnitRunner
```

`scripts/collect-slowdown.ps1 -Serial 7b42a7e6 -DurationSeconds 1900` を併用する。15秒ごとのPSS・Java/native内訳・CPU・温度・thermal status・gfxinfoと、上限付きのlogcatスナップショットを採取する。各コマンドの採取時間も記録する。開始・終了時に終了履歴を採取し、ログ消去やアプリ停止は行わない。API 29では未対応のexit-info出力を証拠不足として扱い、理由を推定しない。

samples/logcat/exitsの各ストリームは最大2 MiBを4世代、metadataは1ファイル。logcatは重複する末尾1500行を採取し、1回の出力は末尾196608文字までに制限する。全期間の完全なログ保存ではない。ローテーションは人工データ12回の追記で4ファイル・各2 MiB以下になることを確認した。

`LongNotePerformanceTest.optInMixedEndurance` は `endurance=true` で有効になる。`durationSeconds`（既定1800）、`iterations`、`idleSeconds`、`fixture=sparse|many|dense|image`、`cacheMode=LIMITED|VISIBLE|NEARBY|ALL` を指定できる。少数24画、多数10000画、少数だが1画8000点、画像入りの合成データを使い、実際のSTYLUSイベント・消去・Undo/Redo・表示位置と倍率の変更・View再生成・放置を反復する。これは保存先を持たない描画／編集の試験であり、保存済みノートの切替や同期の試験としては扱わない。

`EnduranceTelemetry` はフレーム時間の最大4096サンプルからp50/p95/p99を出し、15秒ごとのUI往復時間・Java/nativeヒープ・PSS・GC・CPU時間・thermal status・読み込み数を同じepoch/elapsed時刻で記録する。端末内のJSONLは2 MiBを2世代に制限する。タイル生成中やRenderThreadが参照を残したBitmapを含む全メモリ量を、タイル保持バイト数から推計してはいない。

## 実ノートの扱い

検証版に以前展開した `note-list-benchmark-*` のコピーと、その入力ZIPを使用する。ZIPのSHA-256は `7f82750bf7fbd6fe6c83e4304fb2164c3e6448171467007594c31a53ef5e9f96` で、既存の記録と一致した。現在の本番ノートと内容が同一であることは意味しない。

全試験後にもZIPのSHA-256が同じであることを確認した。本番アプリは試験前後とも0.7.0のままだった。

`RealNoteFrameTest` に `sourceDirectory` と `sourceTitle` を指定すると、そのノートの参照オブジェクトを検証版cache内の新しいストアへストリームでコピーする。コピー元の各オブジェクトのハッシュとheadのハッシュを確認し、元のストアへ編集を保存しない。`durationSeconds`、`iterations`、`idleSeconds` でスクロールと放置を反復し、その後ズームと任意の筆記を行う。筆記は反復区間の後であり、30分間筆記を続ける試験とは異なる。

「解析学基礎2」のコピーは8154画を含み、2往復の計測、ズーム、12接触の筆記、保存後の全既存行と追加行の照合に成功した。`preserveResult=true`で結果を一時保存し、次のinstrumentationプロセスの`reopenPreservedResultInANewProcess`（`verifyPreserved=true`）で8166画の参照・本文ハッシュとストア全体の整合性を確認した。PIDは24710から25291へ変わった。検証後に結果用の一時領域を削除した。

同じ入力コピーでプレビュー有効の試行も成功した。新しい12画のプレビュー内のマゼンタ画素は0から1792へ増え、保存後の8166画を次のプロセスでも検証した。この2試行は短い機能確認であり、プレビューの負荷を温度条件まで揃えて比較した試験ではない。

「解析学基礎演習(類題)」は11月9日のコピーに存在せず、未入手。同名とみなせる証拠のない「解析学基礎2演習」で代用していない。対象名不在によるテスト失敗は、アプリの描画や保存の失敗とは数えない。

## 残る描画待ち

高密度24画の開始直後には約3.8秒、再表示時にも約1.5〜2.4秒のUI往復待ちを記録した。同期を設定していない合成試験で起きており、外部同期OOMの修正だけでこの待ちまで解消したとは言えない。

試験途中の短い2ms間隔のメソッドサンプリングでは、`InkCanvasView.onDraw` → ベクトルフォールバック → `StrokeRenderCache` → `InkStrokeRenderer.LocalRenderer.draw` の経路に最大約3.7秒のスライスがあり、`StrokeLocalCoordinates.create`、Native Strokeの生成、InkのPath生成も記録された。これは包含時間を持つサンプリング結果で、行ごとの時間を加算したCPU内訳にはしていない。サンプリング操作の開始・終了epochを別ファイルへ保存し、通常区間とは区別する。初回は出力が空だったため採用せず、停止後の書き出し待ちを設けた再試行の944229 bytesを解析した。

この描画待ちの修正、タイル生成中・置換後のBitmapを含む所有元別のピーク量、実ノートの全履歴を含む外部同期の長時間比較、キャッシュ4設定とプレビュー／同期の全条件比較は未完了。筆跡の精度やフォールバックの完全性を変える修正、固定ストローク数による制限、一律のキャッシュ無効化は採用していない。

実際のExternalStorageProvider自体のOOMは、仮想Providerの結果から解消済みとは言えない。今回の修正も外部保存先の全件列挙は行う。キャッシュ4設定、プレビュー、外部同期の全組み合わせや、物理ペンでの操作感を網羅した結果ではない。
