# 保存・同期の高速化、軽量化、情報保護の前例調査

調査日：2026-11-04。公式資料と現在のMisq notesの実装・仕様を比較した。以下の構成案は提案であり、この調査によって保存形式や本番データを変更していない。

後続の[複数端末を前提にした設計レビュー](storage-architecture-review-20261104.md)で、回収・分岐・受信順序・長期オフライン復帰・形式移行に未確定事項を整理した。この案だけを実装仕様として使わず、レビュー中の最小仕様を先に固定する。

## 提案の要点

Misq notesには、**本文を共有する不変データ、差分の変更記録、小さな確定情報、独立した世代バックアップ**を組み合わせる方式が有力である。`.recovery`というディレクトリやノート全文の復旧コピーを保存仕様の中心に置く必要はなくなる。ただし、確定状態の選択・同期基準・誤操作からの復旧・媒体破損への備えは、それぞれ設計として残す。

現在の固定長ブロック転送は、この方向への一歩である。一方、巨大化したMISQ0002全体の分割と、別の`.regions`へ本文を再保存する構成は、索引・履歴・本文・読み込みキャッシュの重複を残す。保存・読み込み・同期が同じ本文オブジェクトを使う構成を試作して比較する価値がある。

## 1. SQLite：小さな変更の追記と、後からの再配置

WALは変更ページをログへ追記し、後で本体へ反映する。通常の保存と大きな整理を分けられる。読み手が使っている範囲をチェックポイントが上書きしない設計も参考になる。ただしWALは同じホスト上での共有メモリ等を前提とし、ネットワークファイルシステム上での複数ホスト利用には対応しない。[SQLite WAL](https://www.sqlite.org/wal.html)

耐久性の設定にも注意が必要である。WALの`synchronous=NORMAL`はアプリのクラッシュへの耐久性と、停電・OSクラッシュへの耐久性が同じではなく、後者で直近のコミットが戻る場合がある。`FULL`はコミットごとの同期を追加する。高速化のために永続化の保証を下げた結果と、書き込み量そのものを減らした結果を混同してはいけない。[SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)

**取り入れる案**：端末内では少量の変更を先に耐久保存し、重い索引再構成やパック整理を後で行う。SQLiteの採用自体は比較候補とし、現在のローカル保存方式を置換するかは測定して決める。外部フォルダへ置いたSQLiteのDB・WALを同期ソフトで共有する構成にはしない。

## 2. restic：本文を共有し、世代は参照で保持する

resticは内容に基づくIDでデータを参照し、複数世代で同じデータを共有する。書き込み順序は本文パック、索引、最後にスナップショットであり、確定情報が指すデータを先に揃える。パックのヘッダーから配置索引を再構築できる点も参考になる。[restic repository design](https://restic.readthedocs.io/en/stable/100_references.html#design)

世代を忘れる操作と、使われなくなったデータを物理削除する操作は分離している。整理は排他ロックを伴い、通常のバックアップとの競合を防ぐ。これは、共有する保存先で「2回未参照だったから削除してよい」と判断するだけでは不十分だと考える根拠になる。[restic snapshot removal and prune](https://restic.readthedocs.io/en/stable/060_forget.html)

**取り入れる案**：本文は一度だけ保存し、各世代は必要な本文への参照と管理情報を保持する。多数の小ファイルは適度なパックへまとめる。再配置では新パックを作成・検証し、参照を切り替えた後に旧パックを回収する。

resticの方式も、任意の同期フォルダへロックファイルを置けばそのまま安全になるわけではない。独立したフォルダの複製間では、ロックが他端末へ到着する前に双方が処理できる。この点はMisq notes側の推論であり、共有バックエンドに対する排他制御とは分けて設計する。

## 3. Automerge：変更を蓄積し、取り込めた変更だけを再配置する

Automerge Repoは差分とスナップショットを別のキーで保存する。再配置では自分が読み込んで取り込んだ差分だけを削除し、途中で別の書き手が追加した未知の変更を消さない。世代の同一性に変更の集合を表す情報を使う。[Automerge storage model](https://automerge.org/docs/reference/under-the-hood/storage/)

バイナリ形式は変更履歴の反復性を利用した列単位の格納・圧縮を採用する。履歴を残すことと、冗長な文字列で繰り返し保存することは別問題である。[Automerge binary document format](https://automerge.org/automerge-binary-format-spec/)

**取り入れる案**：現在の対象ID・操作ID・削除記録・親操作の関係を維持しながら、UUIDやペン設定を辞書化し、変更履歴を差分保存する。全履歴と索引を毎回丸ごとJSONへ書き出す量を減らす。Automerge全体の導入や筆跡の全入力点のCRDT化を採用すると決めたものではない。

再配置でファイルをまとめることと、変更履歴を捨てることも区別する。過去の筆跡本文をどこまで残すかは、復旧機能・Undo・端末間統合の仕様として別途決める。

## 4. Syncthing：変更ブロックの転送、受信検証、競合の保持

Syncthingはファイルをブロックに分け、SHA-256を使って必要な部分を取得・検証する。競合時には別名のコピーを保持し、利用者の意図をファイルの時刻だけで決めつけて一方を消さない。[Syncthing synchronization](https://docs.syncthing.net/users/syncing.html)

版管理はフォルダ・端末ごとの任意設定で、既定では無効である。また、他端末からの置換や削除による旧版の保存と、自端末内での変更の保護は同一ではない。[Syncthing file versioning](https://docs.syncthing.net/users/versioning.html)

**取り入れる案**：外部への送信側が本文から先に保存しても、別端末で必要な全ファイルが揃ったとは扱わない。受信側は確定情報から参照を辿り、必要な本文が揃った状態だけを公開する。未着と破損を区別し、未着なら以前の正常な状態を使って待機・再試行する。競合する筆跡は上書きせず、両方を保存して利用者が選べるようにする。

## Androidの外部保存で、前例をそのまま使えない点

ContentResolverの`r`・`w`はパイプやソケットを返す場合があり、モードの実装にもプロバイダー差がある。リネームのサポートも能力フラグで示される。通常のローカルファイルと同じシーク・ロック・置換の性質を、すべてのDocumentsProviderへ仮定することはできない。[ContentResolver](https://developer.android.com/reference/android/content/ContentResolver#openFileDescriptor(android.net.Uri,java.lang.String)), [Document capabilities](https://developer.android.com/reference/android/provider/DocumentsContract.Document#FLAG_SUPPORTS_RENAME)

したがって提案は、端末内の耐久保存と外部への公開を分ける。外部では不変の新ファイルを作り、確認後に新しい確定情報を追加する。書き込み後に読めたこと、停電後にも残ること、別端末やクラウドへ届いたことは異なる。任意のSAF保存先に対して、読み戻し成功だけで媒体やクラウドの耐久性まで保証できるとは扱わない。対応する保存先ごとに検証条件を定める必要がある。

## Misq notes向けの構成案

```text
筆記中の変更
    → 端末内の小さな耐久ログ
    → 変更された本文オブジェクトだけを外部へ保存
    → 必要な参照が揃った確定情報を公開
    → 整理・圧縮は後で実行
```

1. **本文の正本を一本化する。** 筆跡・画像を不変オブジェクトとして保存し、世代と位置索引が同じ本文を参照する。読み込み用に`.regions`へ本文をもう一式保存する必要を減らす。
2. **筆跡レコードを理解したパックと、固定長分割を比較する。** 現行MISQ0002の固定1 MiB分割は、先頭の確定領域や再配置で大きな再書き込みを生じ得る。筆跡や位置のまとまりで不変パックを作る方式、内容に応じて境界を決める方式も測定する。変更に巻き込まれるデータ量と、小ファイルの個数・I/O回数の両方を測る。
3. **表示用索引と、意味を持つ原本を分ける。** 位置索引やオブジェクトの配置索引は再生成可能にする。一方、採用する筆跡の集合・描画順・削除と移動の履歴・ノート名などは原本であり、「索引だから捨てられる」と扱わない。
4. **確定情報と履歴を小さく保つ。** 世代ごとに参照と差分を保存する。辞書化・バイナリ化・必要な範囲ごとの圧縮を比較し、全体圧縮で部分読み込みを妨げないようにする。
5. **同期と回収の参加者を明確にする。** 単一端末では現在の有効化設定を使える。複数端末では各端末の同期基準と読み取り中・送信中の参照を保護し、回収についての合意や排他制御が成立するまで物理削除しない。長期間オフラインの端末を日時だけで不要扱いにしない。

この構成なら、`.recovery`内のノート全文コピーを必要とせず、小さな確定情報と共有する本文で世代を保持できる。ただし、新しい名前のディレクトリへコピーを移しただけでは軽量化にならない。また、共有する本文の寿命を管理する仕組みは引き続き必要である。

## 情報を失いにくくするための層

| 原因 | 必要な仕組み | 単独では足りない仕組み |
| --- | --- | --- |
| 保存途中のアプリ終了・容量不足 | 端末内の耐久ログ、確定前の原本保持、旧世代への復帰 | メモリ上の状態だけの保存 |
| ファイルの未着・途中書き込み | 参照全体の検証、未完了世代の非公開、再試行 | 確定ファイルが1個見えたことだけの確認 |
| 複数端末の同時編集 | 因果関係と削除記録、競合双方の保持、回収の協調 | 更新時刻だけによる勝敗判定 |
| 誤削除・誤った編集 | 時間を遡って選べる復旧点と、その本文の保持 | 最新と直前だけの保存 |
| 媒体故障・共有本文の破損 | 別の保存先の独立したコピー、復元確認 | チェックサムや同じ本文を参照する複数世代だけ |
| 索引の破損 | パックからの配置索引再生成、重要な管理情報の保護 | 索引だけを唯一の情報源にする設計 |

チェックサムは破損の検出に役立つが、失われた本文を作り直すものではない。過去の世代も同じブロックを共有していれば、そのブロックの破損は両世代に影響する。世代保持と独立バックアップは別々に用意する、というのがこの調査からの提案である。

整合性検査は、通常の読取りで使う本文を確認する処理と、アイドル時にデータ全体を順番に巡回する処理へ分ける。resticにも全データの検査と範囲を分けた検査がある。ランダム抽出だけでは全データを必ず検査したとはいえない点も留意する。[restic integrity checking](https://restic.readthedocs.io/en/stable/045_working_with_repos.html#checking-integrity-and-consistency)

## 実装へ進む前の比較試験

SQLiteはOOM、I/Oエラー、クラッシュ、複合故障を試験対象としている。Misq notesでも正常系の速度測定と、故障時に何が残るかの検証を組み合わせる。[SQLite testing](https://www.sqlite.org/testing.html)

- 同じ取得済みノートコピーで、初期表示、追記1筆、削除、移動、サムネイル更新、再配置を比較する。
- 時間の平均だけでなく、遅い側の時間、UI停止、最大メモリ、読み書きバイト数、ファイル操作回数、保存先全体の容量を測る。
- 各書き込み境界での中断、短い書き込み、容量不足、管理情報だけの破損、本文だけの破損を再現する。
- 本文より先に確定情報が届く受信順序、重複到着、長期オフライン後の再接続、端末の時計ずれを再現する。
- パックの再配置と回収の途中で停止し、新旧どちらかの完全な状態へ戻れることを確認する。
- 筆跡の入力データ、安定ID、描画順、削除記録と因果関係の一致を検証し、表示・書き出しでも確認する。
- 独立バックアップから空の保存先へ復元する試験を行う。

性能の改善率と安全性は未測定のため、前例の存在だけで保証しない。最初の試作は本文の正本一本化と、少量の差分保存に絞る。既存形式と読み戻し互換を保ち、移行途中でも旧データから復元できる状態で比較する。
