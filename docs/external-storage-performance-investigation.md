# 外部保存時の保存・削除・ノートを開く速度の調査

後続のブロック保存の実装・実ノートコピーでの比較は[ブロック保存の仕様](block-storage.md)を参照。
初期表示を早める位置別データと遅延読み込みの比較は[位置別読み込みの仕様](spatial-loading.md)を参照。

調査日: 2026-11-03。対象コード: develop `4add5f5`。
ユーザーの申告はテスト版・外部保存。実機のファイル構成の読み取りと、合成ノートによるIO回数の検証を行った。
アプリの変更・インストール・ユーザーノートの保存や削除は行っていない。

## 結論

- 保存・削除後の画面更新は外部保存の完了を待つため、外部IOの負荷がそのまま操作の待ち時間になる。
- ノートを少し変更しただけでも、外部保存ではノート全体を2か所へ書き、検証や表示用コピーの更新のために何度も全体を読む。
- 変更していないノートも保存・削除時に全体を2回読むため、対象以外の大きなノートも待ち時間に影響する。
- 保存済みの内部作業ファイルを解放する仕様により、次に開く際は外部の本文全体を再取得し、全筆跡を復元する。
- 同期処理の一部が保持するロックをメインスレッドから取得する箇所があり、条件次第で画面自体も停止し得る。

## 実機で確認した状態

対象は `net.neomenia.misqnotes.probe`、バージョン `0.1.3-debug`。
外部保存先の `inkdata` には現在のノート1冊があり、サイズは82,116,727 bytes（約78.3 MiB、82.1 MB）。
内部の `files/notes` には本文の `.misq` がなく、外部保存後の作業ファイル解放が実際に起きている。

外部ノートのコミットヘッダーには、世代16の索引4,892,050 bytes、世代15の索引4,892,049 bytesが記録されている。
本文を取得した後も、約9.8 MBの索引JSONの解析と検証、その後の各筆跡のデコード・Ink Stroke構築が必要になる。

`.recovery` は189エントリ、`du -sk` で2,405,328 KiB（約2.29 GiB）。
保存失敗・競合に備えた本文コピーと保存世代の記録があり、古い本文blobを保持し続ける実装になっている。
ただし、毎回2.29 GiB全部を読んでいるわけではない。容量の大きさだけを遅さの主因とは断定できない。
一覧列挙の対象数は増える。

端末上の `sha256sum` で現在の82.1 MBノートを1回読む計測は、ADB往復込みで245 msだった。
これは1回のみの参考値であり、キャッシュ状態が不明で、SAF経由の読み取りや操作全体の所要時間を表す値ではない。

## 合成ノートで確認した読み書き回数

`ExternalIoInvestigationTest` で、実際の `NotebookArchive` と `MisqArchiveDirectory` に読み書き回数を数える `PackedFiles` を接続した。
合成ノート2冊を初回保存した後にカウンターを初期化し、同じArchiveインスタンスで次の操作を順に行った。
初回の追加検証や失敗・再試行がない場合でも、以下のIOが発生した。

| 操作 | 変更対象の可視ノートの全体読み取り | 変更後の本文blobの全体読み取り | 残った未変更ノートの全体読み取り | 本文の全体書き込み | `PackedFiles.names()` |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1冊のタイトル変更 | 3 | 4 | 2 | blobと可視ノートに各1回 | 12 |
| フォルダ設定変更 | 各ノート2 | 0 | 各ノート2 | 0 | 11 |
| 1冊削除 | 0 | 0 | 2 | 0 | 9 |

タイトル変更は全体コピーの負荷を小さな編集で再現するために使用した。
本文blobの4回には可視ノートへコピーするための読み取り1回も含む。
可視ノートの3回には更新前の比較と更新後の検証が含まれるため、すべてが変更後のファイルを読むわけではない。
実機と同程度の82 MBノートなら、この外部層だけでもおおむね574 MB相当の読み取りと164 MB相当の書き込みになる。
ローカルのスナップショット作成、ハッシュ計算、カタログ更新などはこの集計に含めていない。
実機の操作時間は未計測であり、上のIO回数をそのまま秒数へ換算はしない。

## 処理経路と原因

### 保存して一覧へ戻る

`EditorViewModel.closeNote()` はローカル保存、設定保存、プレビュー生成、`NotebookStorage.awaitSync()` を待ってから一覧へ戻る。
ローカル保存キューには500 ms、プレビューには1,000 ms、外部保存には750 msのバッチ待ちがある。
これらは処理の開始時点によって重なるため、単純に合計した値が毎回かかるという意味ではない。
ただし `await()` 自体にバッチ待ちを早める機能はなく、閉じる操作も待機中のキューを待つ。

外部保存では `NotebookStorage.snapshot()` → `ArchiveSnapshot.capture()` が内部にあるノート全文を複製してハッシュを計算する。
外部は内容ハッシュ単位の不変blobなので、小さな追記やタイトル変更でも新しいノート全体をアップロードする。
`MisqArchiveDirectory.commit()` はさらに可視 `.misq` を更新する。
その後の `organize()` が同じ可視ノートを再確認し、変更のないノートもこの2経路で毎回全体ハッシュを計算する。

プレビューは `.misq` 内に保存されるため、プレビューだけが変わった場合もファイルのハッシュが変わって追加の外部保存要求が発生する。
タイミングによっては、本文保存とプレビュー保存が別の外部アップロードになる。

### 削除

`EditorViewModel.listAction()` は削除後も `awaitSync()` が終わるまで一覧を更新しない。
削除対象本文をダウンロードする必要はないが、外部コミットで残った全ノートの可視ファイルを2回読む。
最後の1冊を削除する場合には「残ったノートの2回読み」は発生しない。

内部にファイルが残っている場合、`NoteFiles.deleteNotebook()` は別名コピーの取り残しを防ぐため、全ローカル `.misq` の `readManifest()` を実行する。
この処理は軽量summaryではなく大きな索引の解析に進む。実機確認時はローカル本文がなかったため、この部分の負荷は発生しない構成だった。

### ノートを開く

`ExternalWorkingSet.ensure()` は外部blob全体の取得、全文ハッシュ検証、summary確認、fsyncの後に作業ファイルを配置する。
取得用 `newWorkingSet()` のコールバックは毎回 `MisqArchiveDirectory.names()` を呼び、外部一覧の取得と保存世代JSONの読み取りも行う。

`MisqFile.indexes()` は新旧両方の索引を解析・検証する。
`NoteRepository.load()` は全筆跡を読み、`decodeStroke()` でInk Stroke等を構築してからエディターへ渡す。
各筆跡の読み取りでは個別にRandomAccessFileを開くため、筆跡数の多いノートほど追加コストがある。
`recent` に前回ノートが残っていても、比較用の `files.read()` が先に走るため、解放済み本文の再取得は避けられない。

### ロックの待ち

`NotebookStorage.saveExternal()` はスナップショットの全文コピー・ハッシュ計算と、保存後のカタログ更新をそれぞれ `synchronized(this)` 内で実行する。
カタログ更新でローカルファイルのハッシュが一致しない場合、外部本文の再取得もそのロック内で起きる。
本文の `ensure()` やプレビュー取得も同じロックを保持する。
`openNote()` と `enter()` はメインスレッドから同じロックを取る `keepOpen()` を呼ぶため、IO中のロックを待ってUIを止める可能性がある。
これはコードから確認した条件付きの問題であり、今回ANRや停止時間を実測したわけではない。

## 改善候補の優先順位

1. `commit()` と `organize()` の可視ノート検証重複をなくし、未変更ノートの全文読み取りを減らす。外部からの変更検出と保存後の検証は維持する。
2. 閉じる・削除など明示操作の際に保存キューを即時実行できるようにし、不要なバッチ待ちを短縮する。
3. 本文とプレビューの外部保存をまとめ、同じノートの短時間での二重アップロードを抑える。
4. ローカルで安全に保存した時点の画面更新と、外部保存完了を待つ必要がある処理を整理する。削除記録・保存失敗表示・再試行・復旧の仕様を保つ。
5. `keepOpen()` などメインスレッドが呼ぶ処理から重いIOとのロック競合を除く。索引は正常な最新世代を優先し、旧世代は必要時に解析する。
6. 外部正本の仕様を保ちながら、同一セッションで再度開く際の再取得や筆跡復元を減らす方法を検討する。
7. 復旧blobの整理は別途、保持する世代・競合・中断中の書き込みとの関係を定義してから実装する。今回の調査では削除しない。

## 高速化の実装（2026-11-03）

上記は修正前の調査結果。今回の変更では復旧データの保持方針・形式・整理処理を変更しない。

- 可視ノートの更新と検証を1回に統合し、変更したノートは検証済みのローカルスナップショットから可視ファイルへコピーする。
- 同一保存処理内でアップロード済みblobの検証結果を再利用し、保存後の検証自体は維持する。
- 同じ合成テストで、編集対象関連の外部全文読み取りは7回→3回、未変更ノートの読み取りは2回→1回になった。
- 外部一覧列挙は編集時12回→9回、設定変更時11回→8回、削除時9回→7回になった。
- 明示的な保存待ちではキューのバッチ待機を打ち切る。実行中の書き込みを中断せず、以後の通常保存は引き続きまとめる。
- 外部保存前にプレビュー保存を完了させ、同じスナップショットへ含める。すでに保存済みの追加要求ではスナップショット作成を省略する。
- スナップショットはコピーとハッシュ計算を同時に行い、カタログもそのスナップショットから構築する。編集中の新しい本文を古い外部保存データで置き換えない。
- 通常の読み込みは最新の正常な索引だけを解析する。旧世代は必要な場合に読み、最新世代の破損時には従来どおりフォールバックする。
- 保存した索引を再利用し、ファイルの更新・置換はファイル識別子と高精度の更新時刻・サイズで検出する。
- 全筆跡の読み込みは1つのファイル接続で行い、各筆跡のチェックサム検証は継続する。
- ノートを開く際の外部取得では保存世代JSONの解析を省き、削除対象の別名コピー確認は軽量summaryを優先する。
- 現在のノートIDの更新ではストレージIO用ロックを取得せず、メインスレッドの待機を避ける。

外部正本と内部作業ファイルの解放は継続するため、解放後に開く場合の本文再取得、およびノート単位の外部全文書き込みは残る。
操作全体の体感改善率は上記の読み取り回数の改善率と同じではない。
