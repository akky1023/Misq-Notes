# 実機の発熱比較（2026-11-06）

## 結果

今回の架空ノートと操作条件では、発熱の大きさは **筆記 → ズーム・スクロール → 放置** の順だった。各条件を12分ずつ2回測り、試行前に冷却した。表のCPU・GPU温度は内部センサーの値で、筐体表面の温度ではない。

| 条件 | バッテリー温度（1回目 / 2回目） | CPU温度・終盤3分平均 | GPU温度・終盤3分平均 | アプリ平均CPU使用量 |
| --- | --- | ---: | ---: | ---: |
| 筆記（自動保存を含む） | 27→32℃ / 27→32℃ | 73.9℃ | 66.6℃ | 154% |
| ズーム・スクロール | 27→30℃ / 27→30℃ | 52.5℃ | 43.8℃ | 137% |
| 放置（画面点灯） | 27→27℃ / 27→27℃ | 32.9℃ | 31.8℃ | 6% |

CPU使用量の100%は1コアを使い切る量。2試行の平均であり、電力や発熱量の直接測定値ではない。CPU温度は各読み取り時点のCPUセンサー8個の最大、GPU温度はGPUセンサー4個の最大を使い、その終盤3分を平均した。今回のバッテリー温度の読み取り値は1℃刻みであり、微小な差の判定には使えない。

## 測定条件

- Xiaomi Pad 7（2410CRP4CG、Android 16 / API 36、OS3.0.304.0.WOZMIXM、ADB serial `7b42a7e6`）、検証版 `net.neomenia.misqnotes.probe`、0.1.3-debug、ソース `4ce132226acb44deb3ade4b3f04c83c0a812db7d`。
- 開始時のバッテリー温度27℃を基準とした。これは端末センサーの値であり、室温計による室温測定ではない。
- 同じUSB接続・給電条件、手動輝度の設定値71、画面3200×2136。表示モードは別ログで1分ごとに記録し、取得した値は全て60Hzだった。
- 実際のMainActivityを継承する専用Activityで、通常の編集UI・InkCanvasView・Ink入力・ローカルFormat 3保存・プレビュー更新を使用した。専用フォルダーと専用設定を使い、本番アプリ・既存ノート・外部保存先は変更しなかった。
- 各試行は別の新規ノートとし、同じ乱数種で作った3,600画から開始した。論理幅1,000、筆跡の分布は縦約5,000。初期データ生成・初期保存・先読みの準備による発熱を測定から除外した。キャッシュ設定は既定のNEARBY。
- 順序は放置→筆記→指操作→指操作→筆記→放置。各試行前に画面を消灯し、最低2分、バッテリー27.8℃以下・CPU最大39℃以下・GPU最大35℃以下を30秒間隔で3回確認した。画面を点灯して30秒待ち、開始温度を記録してから操作を開始した。
- 15秒ごとに`dumpsys battery`、`dumpsys thermalservice`のCurrent temperatures from HAL、CPU時間、KGSLのGPUカウンターを記録した。本試験の操作・放置中の取得は計291件。thermalserviceのCached temperaturesには古い値が残っていたため、温度比較には使わなかった。
- CPU時間は`/proc/<pid>/stat`のutime+stimeをCLK_TCK=100で換算し、実測の壁時計時間で割った。試験終了時も計測できるようActivity終了前に10秒待つが、その待機は測定の集計に含めない。
- GPU busyカウンターの読み取り値は原本に保存したが、区間全体の電力量に換算していない。gfxinfoのフレーム数も表示FPSとして扱っていない。

## 筆記と指操作の再現

筆記は完成済みStrokeの直接追加ではなく、STYLUSのDOWN/MOVE/UPイベントを実際のInkCanvasViewへ渡した。1画ごとに基準長12〜100論理単位、方向0〜360度、曲がりの符号・大きさを変え、正弦曲線を重ねて異なる形にした。1画の目標時間150〜650ms、約8ms間隔の入力、ペンを上げる間隔100〜350msとし、筆圧も画の途中で滑らかに変えた。同じ画の使い回しはしていない。乱数種は試行間の再現性のため固定した。

筆記だけの影響を分けるため、筆記条件は固定した表示範囲の中央付近へ追記した。そのため表示中の筆跡密度は時間とともに増える。筆記中に紙送りをする実利用と完全に同じ条件ではない。終了時に追加画数が操作数の80%を超え、保存エラーがないことを確認した。

指操作は1本指スクロールと2本指ピンチを交互に実行した。各ジェスチャーは目標1.2秒の移動と0.3秒の休止で、拡大は約1〜2.4倍、スクロールは上下往復。既存筆跡の表示が継続していることを画面と座標ログで確認した。操作イベントはViewに直接渡すため、ADBコマンド起動を1入力ごとに繰り返す負荷は含まない。

## 判断できる範囲と次の調査

今回の条件では、対策の優先対象は筆記時に動く処理群になる。入力中のInk描画、線の確定、既存筆跡の表示更新、自動保存、プレビュー更新の内訳はまだ分離していないため、特定の関数を主因と断定しない。次はこれらの区間を分けてCPU・描画負荷を測り、重い処理から対策する。

コード上の具体的な候補として、`NoteRepository.immutablePreview`は保存後のプレビュー更新で先頭0〜1000の筆跡を読み直し、サムネイルを描き直す。筆記中のサムネイル再生成をON/OFFした比較は次の切り分け候補になるが、その単独効果は今回測っていない。

この試験は合成ノートをメモリーに載せた状態からの比較で、実ノートの再読込・外部同期・物理ペンの通信・OSの入力配信経路・手の接触は再現していない。各条件2回であり、筆跡密度・倍率・保存先・輝度が異なる実利用すべての順位を保証するものではない。表面温度と電力量も未測定。
