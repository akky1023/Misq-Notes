# 実データ複製による保存方式・起動の検証（2026-10-22）

## 対象と隔離

- Xiaomi Pad 7（2410CRP4CG / Android 16）で、本番の外部保存データを読み取り専用で取得し、検証アプリへ複製しました。本番アプリ・本番保存先への書き込みは行っていません。
- 転送したtarは19,402,752バイト、SHA-256は `745d166c1a067890eb1ff7bb69969b9e29a7b5cb32b56641657b02f6b13ba018` で端末側とPC側が一致しました。
- 外部保存アーカイブの最新の完全な世代を復元した結果、4冊・6,868本の筆跡、管理情報・直前世代などを含む7,196ファイル（3,537,445バイト）がありました。全ファイルのハッシュが保存世代の参照と一致しました。
- 検証アプリのIDは `net.neomenia.misqnotes.probe`、日本語・英語の名前はMisq notesです。生成APKのID・表示名とdebug署名を確認しました。
- 非公開の `files/startup-experiment/seed` に復元元を保持し、`working` を編集用のコピーとしています。実験用SQLiteも同じ専用領域に置きます。
- ユーザーの追加許可を得て、共有側にも `Download/MisqNotesExperiment-20261022` を作り、Androidのフォルダ選択で検証アプリへこのフォルダだけのアクセスを付与しました。共有コピーには元のアーカイブの履歴も含みます。
- 実データ・画面画像・生ログはGit管理対象外の `captures/real-data-experiment-20261022/` に保存しています。APKに実データは含めていません。

## 外部確認を待たずに操作する試作

検証専用の `ExperimentActivity` は端末内の編集用コピーから通常のノート画面を開き、外部コピーの一覧取得・ハッシュ照合を別のIO処理で実行します。外部確認は読み取り専用で、自動取り込み・同期の書き込みは実装していません。したがって、外部更新とローカル編集の競合解決はこの試作の対象外です。編集は検証アプリ内の `working` だけに保存されます。

| 実機計測 | 結果 |
|---|---:|
| 同じ画面・同じコピーで外部確認を先に待つ対照条件 | 一覧準備48.183秒 |
| 待たない方式の実機テスト：Activity起動から一覧操作可能まで | 0.940秒 |
| 同テスト：最も大きい3,679本のノートを開く | 3.168秒 |
| 同テスト：並行した外部確認の完了 | 76.211秒 |

試作では一覧を操作可能にした後、外部確認が続いている間に最大ノートを開いて線数を確認し、一覧へ戻ることまで成功しました。外部確認の成功も確認しています。

別途プロセスを終了してから3回起動したとき、OSの最初の画面表示は501・543・549msでした。3回とも最初のUI Automator取得で新規ノートボタンが有効でした。取得自体に約2.4秒かかり、確認終了は起動約3秒後なので、これを厳密な操作可能時刻とは扱いません。アプリ内部の一覧準備ログは約0.3秒でした。ファイルキャッシュの消去や端末再起動はしていません。

対照条件のログでは外部ディレクトリオブジェクトの構築が22.540秒、その後の保存世代の確認までの累計が48.114秒でした。現行コードは `DocumentArchiveDirectory` の生成時に一覧を取得し、`NotebookArchive.latest()` → `names()` でも再取得します。多数の外部ファイルを二度列挙する構造が大きな調査・改善対象です。

外部確認はアクセス経路・キャッシュ・同時処理によって48〜76秒と変動しました。これらを一定の秒数として保証しません。

## 筆跡をまとめた外部保存

最新世代の7,196ファイル分をノート単位でまとめ、約1MiBを目安に分割する試作を実装しました。管理情報と設定も保持し、ファイルパス・長さ・SHA-256・内容を格納します。今回のコピーは6個のパックになりました。

- 実際のSAF経由で、共有コピー内の新しい `experiment-packs-<UUID>` に作成しました。
- 初回パック生成は875.559msでした。
- 全パックをSAF経由で読み、全レコードのSHA-256と参照集合を検証する時間は3回の中央値473.606ms（335.621・473.606・535.578ms）でした。
- まとめた内容が7,196ファイル分の元データと一致することを確認しました。
- この数値は作成済み6パックを開く時間で、従来形式の全履歴の走査と同一処理ではありません。従来形式では履歴を含む約1.4万ファイルを列挙する一方、パックは最新世代だけを格納しています。
- まだ全体スナップショットの試作です。差分パック、整理、世代確定・復旧、旧形式からの移行は本番採用前に実装する必要があります。

## 端末内のSQLite格納

同じ7,196ファイルの内容をSQLiteの行に格納する試作も比較しました。データは既存のチェックサム付き形式のままBLOB列へ保存し、取り出した全件のハッシュを確認しました。

| 操作 | 個別ファイル | SQLite |
|---|---:|---:|
| 全データ読み取り＋ハッシュ検証・3回中央値 | 188.126ms | 64.280ms |
| 最大ノート3,679本の復号・3回中央値 | 982.242ms | 934.835ms |

SQLiteの初回構築は250.795ms、容量は5,795,840バイトでした。最大ノートの比較では、SQLite側も既存マニフェストの線参照を使い、各行から取り出した筆跡を同じInk復号処理へ渡しています。全アプリをSQLite保存へ切り替えた測定ではありません。反復測定ではJIT・キャッシュが温まっており、実際の画面から最初に開く3.168秒とは区別します。

このデータでは端末内の一括読み取りにはSQLiteの効果がありましたが、ノートを開く処理の差は小さく、保存形式の全面変更より起動時の外部待ちの解消と外部のファイル数削減を優先する判断が妥当です。

## 検証版の利用と再実行

- 検証版を実験画面から起動すると、アプリ自身が検証版のアイコンを `ExperimentLauncher` に切り替えます。本番アプリのアイコンは変更しません。
- 通常のMainActivityの起動処理には検証用のオーバーライド箇所だけを設け、本番側の保存方式や起動順序は変更していません。
- `RealDataExperimentTest` の実機テスト3件と既存単体テスト177件が成功しました。実機ではコピー復元の一致、外部確認中の一覧・ノート操作、SQLite格納の一致、SAF経由のパック保存と読み戻しを確認しています。
- 最新APKのランチャー切り替えも端末上で確認しました。検証版の起動先は `ExperimentLauncher`、通常起動の一覧準備ログは308msでした。

```powershell
adb shell am instrument -w -r -e class jp.handwriting.note.storage.RealDataExperimentTest net.neomenia.misqnotes.probe.test/androidx.test.runner.AndroidJUnitRunner
adb shell am start -n net.neomenia.misqnotes.probe/jp.handwriting.note.ExperimentActivity
```

対照条件だけは、Activity起動時に `--ez waitForExternal true` を指定します。実データの復元元コピーと共有コピーへのアクセス許可が必要です。再実行しても既存の編集用コピーを復元元で上書きしません。
