# 保存方式案の弱点：複数端末を前提にしたレビュー

対象は[前例調査と構成案](storage-architecture-precedents-20261104.md)。2026-11-04時点の設計レビューであり、新形式の実装や端末への反映は行っていない。

## 結論

本文を共有し、差分履歴と小さな確定情報を使う方向は有力である。ただし、前例調査の案は構成要素を示した段階で、複数端末向けの同期プロトコルとしては未完成である。特に、不要データの回収、同時にできた確定状態の扱い、長期オフライン端末の復帰、形式移行は実装前に決める必要がある。

`.recovery`という名前をなくしても、保持すべき世代・同期の基準・競合する変更を表す情報は必要である。小さな参照が指す本文まで削除してしまえば、その参照だけでは復旧できない。

## 実装を止めてでも決める項目

### 1. オフライン端末が必要とする本文を回収してしまう

例：AとBが状態S0で同期した後、Bがオフラインになる。Aは編集を進め、S0が古くなったので本文を削除する。BがS0から独立に編集して戻ってきたとき、S0の本文を取得することを前提とした処理では基準参照が切れる可能性がある。

ただし、過去のノート全文コピーが同期に必須という意味ではない。Bに未同期の変更がなければ、Aの最新状態を取得すればよい。Bにも変更がある場合は、両方の最新状態に安定した対象ID・削除記録・変更の因果関係等が十分に含まれていれば、両者から統合できる設計を選べる。

現行の`MisqFile.merge()`でも、筆跡はAとBのイベント履歴を組み合わせて統合する。共通祖先の`base`から使うのはノート名・用紙の旧値である。上位の`MisqMerge`は祖先ファイルを取得し、フォルダやプリセットの統合も旧値を参照する。したがって、現在の全文コピーへの依存は実装上の依存を含む。新方式では筆跡以外にも項目ごとの変更関係を持たせ、祖先ノートの全文取得を不要にできるかを検証する。

「Aの最新2世代から未参照」「2回の走査で未参照」「更新から一定日数経過」は、Bが不要になったことの証拠ではない。端末が眠っていたことと、利用をやめたことも区別する必要がある。

共通祖先の本文を読む統合方式を維持するなら、任意に古い基準からの自動統合を保証しながら、その基準を有限期間で必ず削除することはできない。祖先全文への依存をなくす設計へ変更するか、次のいずれかを仕様にする必要がある。最新状態に必要な統合情報を含める場合も、因果関係や削除記録をどこまで縮約できるかは別途検証する。

- 登録した端末すべての同期基準を保持し、オフライン端末があれば回収を待つ。
- 利用者が端末を明示的に登録解除する。解除された端末の再参加は、未送信の編集を保護してから新規参加として扱う。
- 履歴保持に期限を設け、期限を超えた復帰では完全な自動統合を保証しない。現在状態の再取得と、未送信の変更の救出・確認を用意する。

**初期実装案**：共有先での物理回収は無効のまま、本文の共有と差分保存を先に導入する。端末登録・再参加・回収の合意を仕様化した後に共有先の自動回収を追加する。

### 2. 同期フォルダのファイルでは、端末間の排他を保証できない

AとBが通信できない間、それぞれのフォルダには相手のロックが見えない。双方がロックを作れてしまう。後でロック同士が同期しても、既に実行した削除は取り消せない。

resticは整理に排他制御を要求するが、これは任意の複製フォルダ上で同じ排他が得られるという意味ではない。[resticの読み書き・整理順序](https://restic.readthedocs.io/en/stable/100_references.html#read-and-write-ordering)

Automergeが同時に再配置できるのは、取り込んだ変更だけを削除することや、CRDTの保存・統合規則を組み合わせているためである。圧縮の手順だけを借りても、Misq notesの本文回収が安全になるとは限らない。[Automerge storage](https://automerge.org/docs/reference/under-the-hood/storage/)

**修正案**：同期ファイルを使う場合は、参加端末が同意した回収の境界を設け、そこまでの変更と必要な本文を保持したことを確認する。読み取り中・送信中・バックアップ中の参照も保護する。応答しない端末は自動で無視しない。強い排他を提供するサーバーを使う方式は別の選択肢として比較する。

### 3. 「最新」を一つの番号やファイルへ上書きすると分岐を失う

例：AとBが共通の世代10から、別々の世代11を作る。更新時刻や端末名の大小で一方を最新とすると、もう一方の変更が見えなくなる。一つのHEADファイルの上書きだけに依存する構成も同じ問題を持つ。

現在の実装は同じ番号の確定世代が複数ある場合に停止する。これは変更を保護する動作だが、新方式でも「止まって保護する」「両方の枝を統合する」の扱いを明記する必要がある。

**修正案**：確定状態を内容に基づくID等で識別し、親となった確定状態のIDを記録する。分岐中は両方の先端を保持する。統合した確定状態は両方を親に持ち、単なる世代番号順で古い枝を削除しない。最新位置を示すファイルは再生成できる案内として扱い、唯一の原本にしない。

### 4. 送信側の保存順序が、そのまま受信側での到着順序にはならない

例：Aが本文P、索引I、確定情報Cの順に保存しても、BではCだけが先に見える。その段階で画面を切り替えると、ノートや一部の筆跡が欠ける。未着を空のノートとみなして保存し直すと、本当の情報消失へつながる。

Syncthingはファイルとブロックを同期する仕組みであり、複数ファイルから成るMisq notesの確定状態を一つの取引として解釈する機能ではない。[Syncthing synchronization](https://docs.syncthing.net/users/syncing.html)

**修正案**：受信側はCから参照する必要な情報の集合を検証し、揃った確定状態だけを採用する。部分読み込みでは、全文を取得済みであることと、必要な参照の所在を確認できることを区別する。画面外の本文を未取得でも、その参照を保存時に保持する。未着・破損・権限エラーを区別し、以前の正常な状態を残して再試行する。

### 5. 再配置後に、古い読取りやバックアップを壊す

例：AがパックPをQへまとめ直し、全体の配置索引を切り替えてPを削除する。B、バックアップ処理、あるいは同一端末の読み込み処理が古い配置索引を保持していれば、次の読取りが失敗する。

**修正案**：本文の論理IDと保存先パックのID・位置を分ける。読取りは特定の確定状態と配置情報に固定する。新パックを作って検証し、参照を公開した後、古い参照を使う処理と保護世代がなくなるまで旧パックを残す。バックアップも固定した確定状態から必要な本文を集め、全体を検証してから完了扱いにする。

単に参照カウンターを各端末で増減させるだけでは、未着・重複・中断で値がずれる。残す確定状態と進行中の処理が必要とする参照から、実際に使う本文・パックを判定する方式が必要である。

### 6. 旧版アプリの保存・自動整理と新形式が衝突する

例：新しいパックや索引の形式を旧版が理解できず、未使用と判断して削除する。旧版が古い形式へ保存し直して、新版の変更を分岐させることもあり得る。

**修正案**：新形式は独立した保存先の領域で試作し、旧形式を保持したまま検証する。形式・機能のバージョンと最低書込み対応版を定義し、未対応形式を読めないアプリは保存も回収もしない。共有する端末すべての更新と移行確認が終わるまで、旧原本を削除しない。既に配布済みの旧版に、新しい制約が自動で効くとは考えない。

## その他の重要な弱点

### 同期ソフトとの責任分担と、単独ファイル方式の再比較

Syncthingは受信内容を一時ファイルへ書き、完成後に配置する。一つのファイルを受信する途中の状態と、複数の関連ファイルの一部だけが揃った状態を混同してはいけない。後者の関連を定義したのはアプリ側であり、同期ソフトがファイルを正常に同期していてもアプリ側で対処が必要になる。また、アプリが不要と判断して削除したファイルについて、同期ソフトがその削除を他端末へ反映するのは通常の動作である。[Syncthingの一時ファイルと同期](https://docs.syncthing.net/users/syncing.html#temporary-files)、[同期対象](https://docs.syncthing.net/users/faq.html#what-is-syncthing)

そのため、同期ソフトを前提にする構成では、自己完結した1ノート1`.misq`を保存し、差分転送を同期ソフトへ任せる方式も比較対象へ戻す。Syncthing自身がブロック差分を転送するので、アプリ側で外部の本文を多数のファイルへ分割することだけが差分転送の手段ではない。ただし、外部フォルダへ書くアプリ側の書込み量と、端末間のネットワーク転送量は別である。単独ファイル方式で全文のコピーやハッシュ計算が増えれば、端末の保存処理は遅くなり得る。SAF上の保存中断対策、同時編集のマージも引き続き必要になる。

比較する構成は「自己完結ファイル＋同期ソフトの差分転送」と「アプリ管理の不変パック＋確定情報」の両方とし、既存の全量外部保存の計測も参照して決める。後者の容量・I/O削減が、その依存関係と回収を管理する複雑さに見合うかを確認する。

| 弱点 | 起こり得ること | 設計へ加える条件 |
| --- | --- | --- |
| 削除記録の早すぎる整理 | 古い端末が持つ筆跡・ノートが復活する | 削除した事実と因果関係を保持し、整理の境界と再参加の扱いを定義する |
| 小さな確定情報という前提 | 全筆跡への参照を毎回並べれば、参照だけでも巨大化する | 差分と構造を共有する索引、一定間隔のスナップショットを比較する |
| 履歴の無期限保持 | コピーの重複を減らしても、過去の編集本文で容量が増える | 表現の圧縮と、復旧できる期間・粒度の変更を分離する |
| 小ファイルが多すぎる | SAFや同期のファイル操作回数が増えて遅くなる | 適度なパックへまとめ、サイズ・操作回数・初期表示を一緒に測る |
| パックが大きすぎる | 小さな編集や表示で、大量の転送・展開・再配置が発生する | 個々の本文を独立して取り出せる構造と、保存先に応じたパックサイズを検証する |
| 索引に意味情報を持たせすぎる | 索引の再生成時に、描画順や削除・移動の意味を復元できない | 位置・配置のキャッシュと、採用する筆跡の集合・順序・履歴の原本を区別する |
| 位置索引の世代がずれる | 正しい本文があるのに見えない、未読データが古い状態で戻る | 確定状態と索引形式を対応付け、部分編集の追加・削除を古い読取りより優先する |
| ペン設定の辞書IDが端末依存 | 同じ番号が別のブラシを意味し、見た目が変わる | 辞書の定義を保存・同期し、内容や形式に結び付いた安定した識別方法を使う |
| 正規化や再エンコードの差 | 同じ筆跡でも端末・ライブラリ更新でIDや形状が変わる | 既存の入力データを保ち、表現形式・数値・圧縮と論理的な識別を定義する |
| ライブラリ情報の統合不足 | ノートの所属やフォルダ階層が壊れ、ノートが見えなくなる | 筆跡以外の名前・所属・用紙・階層の同時変更も仕様化する。階層の循環を拒否する |
| ノート全体の確定範囲が不明 | 用紙だけ新しく本文が古い等、中間状態を表示する | 同時に確定させる項目の単位を決め、独立したノートの編集まで不要に競合させない |
| バックアップが作業データと同じ寿命 | 自動回収が復旧用データまで削除する | 独立した保存先と保持方針、復元確認を用意する |

共有本文の破損は、それを参照する複数世代へ同時に影響する。確定情報の二重化は重要だが、本文の独立した複製を代替しない。逆に独立バックアップがあっても、同期処理で変更を上書きしてよい理由にはならない。

## 現在の自動整理との区別

検証版へ実装した`RecoveryCleanup`は、単一端末専用の有効化設定、端末内の同期基準とバックアップの保護、2回の未参照確認を使う。別端末の基準を収集する機能や、端末間で回収に合意する機能はない。ファイル一覧の変化を確認しても、確認直後に別端末が公開する変更との競合まで排除できるわけではない。

そのため、この処理を新方式の複数端末向け自動整理へ流用してはいけない。共有先で無効にする現在の制約は維持する。

## 実装前に固定する最小仕様

1. 確定状態のID、親子関係、複数の先端、確定情報を失ったときの復旧方法。
2. 筆跡・ノート・階層・用紙等の同時変更についての統合と競合の規則。
3. 部分受信・部分読み込み・未送信の変更を保持した状態からの保存規則。
4. 端末の識別・登録・登録解除と、古い状態から再参加する手順。端末の複製やバックアップ復元時の識別も含む。
5. 読取り・送信・バックアップと、パック再配置・物理削除を調整する手順。
6. 形式移行と、旧版が書込み・削除しないことを保証する切替手順。

最初の試作では、共有先の物理回収を実装せず、不変の本文と確定状態の分岐を保持する。これにより回収に起因する消失を避けて、保存・読取り・統合の正しさと実際の容量削減を先に測れる。ただし、保持による容量増加や媒体破損まで解決したとは扱わない。

## 最低限必要な試験シナリオ

- AとBがオフラインで同じ筆跡を別々に移動し、受信順序が逆でも両方を保持して同じ競合判定へ到達する。
- Aが削除、Bが古い状態で編集し、削除記録の再配置後にBが復帰する。
- 本文・配置索引・確定情報を全順序で到着させ、重複や途中欠落も含めて確認する。
- Bが長期間オフラインの間に、Aが何度も再配置する。Bを登録解除した場合としない場合を分ける。
- 読取り・アップロード・バックアップが古いパックを使っている途中で整理する。
- 公開と削除の各境界で強制終了・容量不足・読取りエラーを発生させ、再試行の結果を確認する。
- 端末の時計ずれ、端末データの複製、バックアップからの復元、旧版の再接続を再現する。
- 独立したバックアップから、端末内のキャッシュや同期基準を持たない新規環境へ復元する。

試験では、最終画面の一致だけでなく、採用・競合・削除された筆跡のID、本文、描画順、因果関係、参照先の存在を照合する。途中で消えた枝が後の統合で無視されていないことも確認する。
